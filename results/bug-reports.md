Составлены на основе 3 падений реального прогона `tests/main-screen/non-authorized-user.spec.ts`
от 2026-11-20 (см. `results/test-cases.md`). Черновики для заведения в трекер — решение,

## BUG-01: Список депозитов возвращает элементы с невалидными свойствами продукта

**Связанный тест-кейс**: TC-05 (ID 6691)
**Связанное требование**: АС-11 («Неавторизованный пользователь может видеть каталог банковских
продуктов... информацию о депозитах»); US-3.1 | Umbraco - Content Deliver API, общие свойства
продукта (entityTitle, description, url, image)
**Окружение**: тестовый стенд проекта
**Severity**: Major (кандидат) — затрагивает отображение каталога продуктов на главном экране для
всех неавторизованных пользователей, не блокирует работу приложения целиком.
**Приоритет**: уточнить с продакт-/QA-лидом.

### Предусловие
Пользователь не авторизован, запрашивает список продуктов типа «депозит».

### Шаги воспроизведения
1. Запросить список контента с фильтром по типу продукта «депозит» и языком RU.
2. Получить список элементов из ответа.
3. Для каждого элемента проверить обязательные свойства продукта: `entityTitle` (непустая
   строка), `description` (непустая строка), `url` (непустая строка), `image` (непустой массив).

### Ожидаемый результат
Все элементы списка депозитов проходят валидацию — 0 ошибок по обязательным полям.

### Фактический результат
```
expect(response.body.items).toHaveLength(0) после фильтрации по валидным свойствам —
Expected length: 0, Received length: 4 (["url","url","url","url"])
```
4 из элементов списка депозитов не прошли валидацию — тест сообщает об ошибке именно в поле
`url` у всех четырёх (автоматика не детализирует конкретное значение, только название
непройденной проверки).

### Доп. материалы
`test-results/main-screen-non-authorized-d2fa6--Получение-списка-депозитов-api-tests-parallel/error-context.md` (локально после прогона).

## BUG-02: Запрос дочерних элементов каталога продуктов возвращает пустой список

**Связанный тест-кейс**: TC-20 (ID 19648)
**Связанное требование**: US-3.1 | Umbraco - Content Deliver API, раздел 2.4 «Параметры запроса»
(опция извлечения непосредственных дочерних элементов указанного узла)
**Окружение**: тестовый стенд проекта
**Severity**: Major (кандидат) — если эта опция реально используется мобильным приложением для
построения каталога продуктов, это блокирует отображение всего раздела; если используется
только служебно/не на проде — ниже, Minor.
**Приоритет**: уточнить с техлидом, используется ли эта опция в реальном клиентском флоу
главного экрана, или только в тестовом/служебном коде.

### Предусловие
Корневой узел каталога продуктов существует в CMS и имеет дочерние элементы (карты/кредиты/
депозиты) — это подтверждается тем, что обычная выборка всех потомков этого же узла (TC-01…
TC-05, TC-26) в этом же прогоне вернула непустые списки.

### Шаги воспроизведения
1. Запросить непосредственные дочерние элементы корневого узла каталога продуктов.
2. Проверить общее количество элементов в ответе.
3. Проверить, что тип каждого элемента входит в ожидаемый набор (карта/кредит/депозит).

### Ожидаемый результат
Количество элементов > 0; возвращённые элементы — непосредственные дочерние узлы корневого узла
каталога продуктов.

### Фактический результат
```
expect(response.body.total).toBeGreaterThan(0) — Expected: > 0, Received: 0
```
Запрос вернул общее количество элементов равным 0 — пустой список.

## BUG-03: Фильтрация по диапазону даты создания не возвращает продукты из текущего диапазона

**Связанный тест-кейс**: TC-24 (ID 19652)
**Связанное требование**: US-3.1 | Umbraco - Content Deliver API, раздел 2.4 «Параметры запроса»
(фильтрация по диапазону даты создания)
**Окружение**: тестовый стенд проекта
**Severity**: Major (кандидат) — если фильтрация по дате создания используется в реальных
сценариях (например, «новые продукты»/баннеры по срокам действия), это ломает соответствующую
функциональность.
**Приоритет**: уточнить с техлидом область реального использования фильтра по дате создания.

### Предусловие
В каталоге продуктов есть элементы, попадающие в широкий текущий диапазон дат — это заведомо
так, поскольку соседние тесты того же прогона (TC-01…TC-05, TC-19, TC-26) подтверждают, что
продукты в каталоге существуют и доступны по умолчанию.

### Шаги воспроизведения
1. Запросить все элементы каталога продуктов с фильтром по широкому текущему диапазону даты
   создания.
2. Отдельно запросить то же самое с заведомо будущим диапазоном даты создания.
3. Сравнить количество элементов в обоих ответах.

### Ожидаемый результат
Текущий диапазон возвращает непустой список (> 0 элементов); будущий диапазон — пустой список
(0 элементов, так как продуктов "из будущего" быть не может).

### Фактический результат
```
expect(currentRange.body.items.length).toBeGreaterThan(0) — Expected: > 0, Received: 0
```
Будущий диапазон корректно вернул 0 (это прошло без ошибки) — но и текущий широкий диапазон
тоже вернул 0, хотя продукты в каталоге точно существуют.

---

**Общее примечание по всем трём**: ни один из трёх кейсов не похож на ошибку самого автотеста —
логика проверки симметрична уже проходящим соседним тестам (TC-01…TC-04, TC-19, TC-21, TC-23,
TC-26), которые бьют по той же фиче и тому же API теми же методами и проходят.
