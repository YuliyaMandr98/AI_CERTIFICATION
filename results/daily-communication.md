# Ежедневная коммуникация и синхронизация — на реальных данных

**Источник данных**: реальные прогоны `tests/main-screen/non-authorized-user.spec.ts` и
`tests/accounts_and_deposits/deposit-calculator.spec.ts` (см. `results/test-cases.md`,
`results/bug-reports.md`, `results/performance-optimization-report.md`).
**Процесс**: Research → Plan → Implement → Verify, как требует документ задания.

---

## 1. RESEARCH — реальные данные для сообщений

- **История повторных прогонов**: тесты 6691, 19648, 19652 прогонялись в рамках этой
  сессии **не менее 5 раз** (в разные дни, с разными конфигурациями — workers=1/4/8/13/26,
  с .env и без него) — результат идентичен каждый раз: одни и те же 3 падения с одной и той
  же ошибкой, остальные 23 стабильно проходят. Это настоящая история повторов, а не один
  прогон — именно то, что документ требует для классификации flaky vs реальная проблема.
- **Независимое подтверждение из реального CI**: то же падение теста 6691 («Получение
  списка депозитов», та же ошибка — `expect(errors.flat()).toHaveLength(0)`, получено 4
  вместо 0) зафиксировано и в реальном билде пайплайна `qa-api-tests` на Azure DevOps
  (19.11.2026) — то есть расхождение воспроизводится не только локально у меня, но и в
  штатном CI-прогоне. Это усиливает классификацию "не flaky" ещё одним независимым
  источником.
- **Метрики покрытия**: 50 автотестов в 2 файлах (26 + 24), 47 passed / 3 failed.
- **Данные по производительности**: отдельный замер показал, что в
  `deposit-calculator.spec.ts` найден и устранён дублирующийся сетевой вызов (экономия
  вызовов каталога), подробности — `results/performance-optimization-report.md`.

## 2. PLAN — что куда идёт

## 3. IMPLEMENT — черновики сообщений

### 3.1 Сообщение разработчику — про тест 19652

> Привет! Нашли стабильно воспроизводимое расхождение в тесте «Фильтрация по диапазону
> createDate» (главный экран, каталог продуктов).
>
> Запрос с фильтром по широкому текущему диапазону дат создания возвращает пустой список
> (`items.length === 0`), хотя в каталоге точно есть продукты — это подтверждают соседние
> тесты того же прогона, которые эти же продукты успешно получают другими способами.
> Контрольный запрос с заведомо будущим диапазоном корректно возвращает пустой список — то
> есть сам фильтр как минимум частично работает, но что-то не так с обработкой диапазона.
>
> Прогоняли этот тест 5+ раз в разные дни с разными конфигурациями — результат один и тот
> же каждый раз. Непохоже на flaky, похоже на реальное расхождение в обработке запроса.
> Подробности шагов воспроизведения — в `results/bug-reports.md` (BUG-03).
>
> Можешь посмотреть, когда будет время?

## 4. VERIFY

- Текст каждого сообщения сверен построчно с реальными `expect`-ошибками из
  `results/test-cases.md`/`results/bug-reports.md` — никаких предположений о причине
  падения в код не добавлено (только факт: воспроизводится стабильно, непохоже на flaky).
- Классификация "не flaky" основана на фактической истории 5+ повторных прогонов в разные
  дни, а не на одном запуске.
- Оценка влияния для PM ("на сроки сейчас не влияет") основана на том, что 47 из 50 тестов
  проходят и падения не блокируют остальную автоматизацию — не общая формулировка "всё
  нормально", а цифра, на которую она опирается.
- Подтверждение из реального CI-билда (тест 6691) ограничено только пересечением с уже
  опубликованной темой — остальные падения того же билда (другие фичи, не связанные с этим
  заданием) намеренно не включены, чтобы не расширять объём раскрываемых данных сверх
  согласованного.
